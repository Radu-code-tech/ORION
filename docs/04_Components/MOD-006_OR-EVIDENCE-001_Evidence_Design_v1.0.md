## 1. Purpose

This document translates the approved MOD-006 OR-EVIDENCE-001 Evidence specification v1.0 into an implementation-ready technical design.

The design defines the internal model, identity mechanism, validation rules, immutability guarantees, storage behavior, deterministic querying, duplicate detection, EventBus integration, error hierarchy, configuration, and testing boundaries.

This document does not introduce trading strategy or decision-making logic.

---

## 2. Design Principles

The implementation shall follow these principles:

1. Evidence before conviction.
2. Determinism before convenience.
3. Immutability after validation.
4. Explicit validation over implicit coercion.
5. Traceability over opaque behavior.
6. Reproducibility over runtime randomness.
7. One responsibility per component.
8. Event transport and evidence integrity remain separate concerns.
9. No trading decision shall be produced by the Evidence Engine.
10. No information shall be silently altered during normalization.

---

## 3. Architectural Responsibility

OR-EVIDENCE-001 is responsible for:

- creating Evidence objects;
- validating Evidence;
- generating deterministic Evidence identity;
- enforcing immutability;
- detecting duplicate Evidence;
- storing Evidence;
- retrieving Evidence;
- querying Evidence;
- providing deterministic ordering;
- optionally publishing validated Evidence through EventBus.

OR-EVIDENCE-001 is not responsible for:

- BUY decisions;
- SELL decisions;
- NO TRADE decisions;
- signal scoring;
- strategy;
- risk management;
- position sizing;
- order execution;
- machine-learning decisions;
- profitability assessment;
- sentiment interpretation.

## 4. Evidence Data Model

The canonical Evidence model contains:

Evidence
├── evidence_id
├── timestamp
├── source
├── type
├── value
├── symbol
├── timeframe
└── metadata


## 5. evidence_id

`evidence_id` shall be a deterministic SHA-256 hexadecimal digest derived from the canonical identity representation of the Evidence.

The identifier is generated by the Evidence Engine and shall not be supplied independently by callers.

Random UUIDs shall not be used as the primary Evidence identity.

The identity rule is:

Evidence identity = SHA-256(canonical identity representation)

The identity mechanism must produce the same identifier for the same semantic Evidence.

---

## 6. Canonical Identity

The following fields are identity-bearing:

- timestamp;
- source;
- type;
- value;
- symbol;
- timeframe.

Metadata is excluded from the identity by default.

Operational or diagnostic metadata must not change the semantic identity of Evidence.

If a future requirement establishes that a metadata field is semantically identity-bearing, that field must be explicitly promoted through a specification or design change.

---

## 7. Canonical Serialization

Canonical serialization shall be:

- deterministic;
- encoded as an exact UTF-8 byte sequence;
- independent of Python object memory address;
- independent of dictionary insertion order;
- independent of platform;
- independent of process;
- independent of execution order.

The canonical Evidence identity representation shall use the fixed version marker:

`ORION-EVIDENCE-1`

The six identity-bearing fields shall be serialized in exactly this order:

1. timestamp
2. source
3. type
4. value
5. symbol
6. timeframe

Each field shall use the following exact framing:

`<field-name>:<byte-length>:<canonical-field-value>`

where:

- `<field-name>` is the literal ASCII field name;
- `<byte-length>` is the number of UTF-8 bytes in `<canonical-field-value>`;
- `<canonical-field-value>` is the canonical value encoding defined in Section 24;
- fields shall be concatenated in the exact order specified above;
- no additional whitespace shall be introduced;
- no locale-dependent formatting shall be used;
- no implicit delimiter shall be introduced;
- Python `str()`, `repr()`, object serialization, memory addresses, or runtime `hash()` shall not be used.

The version marker shall be encoded as the exact ASCII prefix:

`ORION-EVIDENCE-1|`

The trailing `|` is part of the canonical representation and is included in the SHA-256 input.

The six identity-bearing fields shall follow this prefix immediately, with no additional whitespace or separator.

For `symbol` and `timeframe`, an absent value shall be represented using the canonical null representation defined in Section 24.

The complete canonical representation shall be uniquely reconstructible from this specification.

The Evidence identity shall be generated as SHA-256 over the exact UTF-8 byte sequence of the complete canonical identity representation, including the version marker.
## 8. Value Model

The initial implementation shall support objective Evidence values including:

- integer;
- finite floating-point number;
- boolean;
- string;
- deterministic structured values where explicitly supported.

Unsupported runtime objects shall be rejected.

Floating-point values shall be rejected when they are:

- NaN;
- positive infinity;
- negative infinity.

Boolean values shall not be silently interpreted as numeric values.

Structured values shall use deterministic key ordering.

---

## 9. Timestamp Design

Timestamp is mandatory for Evidence identity and ordering.

The implementation shall require a timezone-aware timestamp.

Naive timestamps shall be rejected.

Timestamps shall be normalized to UTC before canonical serialization and storage.

Example:

`2026-01-01T12:00:00+02:00`

shall normalize to:

`2026-01-01T10:00:00Z`

The normalized timestamp becomes part of the immutable Evidence object.

---

## 10. Source Design

`source` identifies the ORION component or objective source that generated the Evidence.

Examples include:

- OR-DATA-001;
- OR-MSE-001;
- OR-RISK-001;
- market_data;
- external_feed.

The implementation shall:

- require a string;
- reject empty or whitespace-only values;
- trim leading and trailing whitespace;
- preserve internal characters exactly;
- reject unsupported runtime types.

The normalized source string becomes identity-bearing.

No fixed enum is imposed in v1.0; producers may introduce new source names without modifying the Evidence Engine.

Source validation shall fail fast.

---

## 11. Evidence Type Design

`type` identifies the semantic category of Evidence.

The initial implementation shall represent the type as a validated string.

The type shall be non-empty after trimming. Leading/trailing whitespace shall be removed; internal content and case shall be preserved. No fixed business enum is imposed in v1.0. The Evidence Engine validates representation, not business semantics.

Examples include:

- market_price;
- market_structure;
- liquidity;
- trend;
- risk_state;
- external_event.

The initial Evidence Engine shall not interpret the business meaning of the Evidence type.

Semantic interpretation belongs to the component producing or consuming the Evidence.

---

## 12. Market Context

`symbol` and `timeframe` are optional at the generic Evidence model level when the Evidence type does not require market context.

When supplied, they shall be validated as non-empty strings after trimming.

`symbol` and `timeframe` are case-sensitive identity-bearing values. The Evidence Engine shall not uppercase, lowercase, expand aliases, or otherwise reinterpret them.

Example:

`symbol: XAUUSD`

`timeframe: M1`

No automatic inference of symbol or timeframe shall be performed.

If a future Evidence type requires market context, that requirement must be explicitly defined by that Evidence type.


## 13. Metadata

`metadata` contains supplementary non-identity information.

Metadata shall:

- be optional;
- be a mapping with string keys;
- contain only supported deterministic scalar, mapping, sequence, or null values;
- be detached from mutable caller-owned structures;
- become recursively immutable after Evidence creation;
- preserve deterministic structure;
- never alter `evidence_id` unless explicitly designated identity-bearing by design.

Metadata mappings shall use deterministic key ordering for canonical storage/inspection while remaining excluded from identity by default.

Examples include:

`feed: provider_a`

`sequence: 12345`

`quality: raw`

Metadata shall not be used by the Evidence Engine for trading decisions.

---

## 14. Immutability

Evidence is immutable after creation.

Immutability applies recursively to:

- Evidence object;
- metadata mapping;
- nested mappings;
- nested sequences;
- nested supported structures.

A caller shall not be able to modify Evidence after creation through:

- direct attribute assignment;
- mutation of nested metadata;
- mutation of a caller-owned input structure;
- mutation through an exposed internal reference.

Attempted mutation shall fail explicitly.

---

## 15. Evidence Construction

Evidence creation follows this sequence:

Input
↓
Type validation
↓
Timestamp normalization
↓
Value validation
↓
Metadata defensive copy
↓
Canonical identity generation
↓
Immutable Evidence object

Evidence shall not become visible to the Evidence Store before successful validation and identity generation.

---

## 16. Evidence Store

The initial store shall be an in-memory deterministic store.

Required operations:

- `add(evidence)`
- `get(evidence_id)`
- `query(...)`
- `count()`
- `clear()`

The store shall maintain Evidence by `evidence_id`.

The store shall not silently replace an existing Evidence object with the same identity.

---

## 17. Duplicate Evidence

Duplicate Evidence is defined by identical canonical identity.

Therefore:

same identity → duplicate

different identity → distinct Evidence

Adding duplicate Evidence shall raise:

`DuplicateEvidence`

The implementation shall not silently overwrite duplicates.

Duplicate detection must be deterministic and independent of insertion timing.

---

## 18. Retrieval

`get(evidence_id)` shall:

- return the immutable Evidence object when found;
- return `None` when the identity is not present;
- never return a mutable internal representation.

`get()` is a non-raising lookup operation. A strict operation that requires presence may raise `EvidenceNotFound`.

The implementation shall not expose internal storage structures.

---

## 19. Query Design

The Evidence Store shall support filtering by:

- symbol;
- timeframe;
- source;
- type;
- timestamp range.

All filters are conjunctive unless explicitly specified otherwise.

Example:

`symbol = XAUUSD`

AND

`timeframe = M1`

AND

`type = market_price`

Query operations shall return immutable Evidence objects.

---

## 20. Deterministic Ordering

Default query ordering shall be:

`timestamp ASC`

then:

`evidence_id ASC`

The timestamp is the primary ordering key.

`evidence_id` is the deterministic tie-breaker.

For descending order:

`timestamp DESC`

then:

`evidence_id DESC`

This guarantees deterministic ordering when multiple Evidence objects share the same timestamp.

Ordering shall not depend on:

- insertion order;
- dictionary order;
- memory address;
- UUID randomness;
- database implementation details.


## 21. Error Model

The Evidence Engine shall expose explicit, deterministic error types.

The initial error hierarchy shall distinguish:

- invalid Evidence input;
- invalid timestamp;
- invalid source;
- invalid Evidence type;
- invalid value;
- invalid symbol;
- invalid timeframe;
- duplicate Evidence;
- Evidence not found.

Errors shall:

- be deterministic;
- identify the violated validation rule;
- fail explicitly;
- never silently normalize invalid input into valid input;
- never silently discard Evidence.

The implementation shall use typed exceptions rather than generic exceptions wherever the failure can be identified semantically.

---

## 22. Validation Rules

Validation shall occur before Evidence becomes visible to the Evidence Store or downstream consumers.

Validation order shall be deterministic:

1. Evidence object structure;
2. timestamp;
3. source;
4. Evidence type;
5. value;
6. symbol;
7. timeframe;
8. metadata structure;
9. canonicalization;
10. identity generation.

Validation shall reject:

- missing mandatory fields;
- unsupported field types;
- NaN values;
- positive or negative infinity;
- invalid timezone information;
- invalid source values;
- invalid Evidence types;
- invalid symbol or timeframe values when supplied;
- unsupported metadata structures.

Validation shall never depend on:

- insertion order;
- process state;
- memory address;
- random values;
- external mutable state.

---

## 23. Evidence Identity and Canonicalization

`evidence_id` shall be generated deterministically from the canonical identity-bearing content of Evidence.

The identity algorithm shall be:

`SHA-256(canonical_evidence_representation)`

The canonical representation shall be generated before hashing.

Canonicalization shall:

- use UTF-8 encoding;
- use a deterministic field order;
- use explicit type representation;
- use normalized timestamp representation;
- use deterministic representation of supported structured values;
- exclude non-identity metadata;
- reject unsupported values rather than silently converting them.

The identity-bearing field order shall remain:

1. timestamp;
2. source;
3. type;
4. value;
5. symbol;
6. timeframe.

The implementation shall never use:

- Python `hash()`;
- object memory address;
- `repr()` as the canonical representation;
- non-deterministic serialization;
- random UUID generation.

Two Evidence objects with identical canonical identity-bearing content shall produce the same `evidence_id`.

Two Evidence objects with different identity-bearing content shall produce different identities except for the theoretical collision properties of SHA-256.

---

## 24. Structured Value Canonicalization

Structured values are supported only when their structure belongs to the explicitly supported deterministic value model.

The initial supported structured values shall include:

- mappings with string keys;
- sequences containing supported values;
- nested combinations of supported deterministic values.

Canonicalization shall recursively normalize supported structures.

For mappings:

- keys shall be strings;
- keys shall be ordered lexicographically by their UTF-8 encoded key bytes before canonical encoding;
- each mapping key shall be encoded using the canonical string encoding defined in this section:
  `S:<byte-length>:<UTF-8 bytes>`;
- values shall be recursively canonicalized;
- mapping key encoding shall be deterministic and shall not depend on dictionary insertion order.

For sequences:

- element order shall be preserved;
- every element shall be recursively canonicalized.

Supported scalar values shall retain explicit type information.

The canonical representation shall distinguish null, boolean, integer, finite floating-point value, string, structured mapping, and structured sequence.

Scalar encoding shall be:
- null → `N`
- false → `B0`
- true → `B1`
- integer → `I` followed by its signed base-10 representation
- finite float → `F` followed by the Python `float.hex()` representation of the finite IEEE-754 binary64 value;
- the representation shall be generated using the exact Python `float.hex()` operation;
- the representation shall be deterministic for a given finite binary64 floating-point value;
- implementations claiming compatibility with this canonical format shall reproduce the same IEEE-754 binary64 value and the same `float.hex()` representation;
- string → `S:<byte-length>:<UTF-8 bytes>`

Structured encoding shall be:
- mapping → `M:<count>:[<key-value pairs>]`, with pairs ordered by UTF-8 key bytes
- sequence → `Q:<count>:[<encoded elements>]`

Counts are non-negative base-10 integers. This encoding explicitly distinguishes boolean from integer, integer from float, null from string, and mapping from sequence.

Unsupported objects shall be rejected.

The implementation shall not depend on:

- Python object representation;
- dictionary insertion order;
- platform-specific serialization;
- locale-specific formatting.

The canonical serialization format is defined by Sections 7 and 24 of this design and is an implementation contract. Tests shall verify that contract; tests shall not define or change it.

## 25. Query Semantics

Query filters shall be applied conjunctively.

For example:

`symbol = XAUUSD`

AND

`timeframe = M1`

AND

`type = market_price`

AND

`source = provider_a`

A query shall return only Evidence objects satisfying all supplied filters.

Timestamp filtering shall use half-open intervals: `[start, end)`. The start boundary is inclusive and the end boundary is exclusive. If only `start` is supplied, the lower bound is inclusive. If only `end` is supplied, the upper bound is exclusive. If both are supplied and `start >= end`, the query shall be rejected as an invalid range.

Query results shall:

- contain immutable Evidence objects;
- be deterministically ordered;
- never expose internal storage;
- never modify stored Evidence;
- return an empty result when no Evidence matches.

Query behavior shall be independent of insertion order.

---

## 26. EventBus Integration

The Evidence Engine owns Evidence semantics and integrity.

The existing EventBus owns event transport.

The Evidence Engine shall not duplicate EventBus responsibilities.

When EventBus publication is enabled:

Evidence shall be:

1. validated;
2. canonicalized;
3. assigned an identity;
4. stored successfully;
5. published through the EventBus.

The EventBus shall receive only valid, immutable Evidence.

Invalid Evidence shall never be published.

The Evidence Engine shall not depend on EventBus implementation details for Evidence identity or validation.

The integration shall preserve deterministic behavior.

---

## 27. Transaction and Atomicity Rules

Evidence storage and EventBus publication shall follow an explicitly defined consistency rule.

The initial implementation shall use:

`store-first, publish-second`

The successful store operation is the commit point for Evidence persistence within MOD-006.

The required sequence shall be:

1. validate Evidence;
2. canonicalize Evidence;
3. generate `evidence_id`;
4. detect duplicates;
5. store Evidence;
6. publish Evidence through EventBus.

If validation or identity generation fails:

- Evidence shall not be stored;
- Evidence shall not be published.

If duplicate detection fails because the Evidence already exists:

- the duplicate shall not replace the existing Evidence;
- the duplicate shall not be published.

If EventBus publication fails after successful storage:

- the Evidence shall remain stored;
- the publication failure shall be observable;
- the Evidence shall not be silently removed;
- the system shall not create a second Evidence identity.

Recovery/retry semantics are outside the initial Evidence Store responsibility and shall be defined by the higher-level orchestration layer.

## 28. Observability and Logging

- Evidence accepted;

Logs shall contain sufficient contextual information to support debugging and audit without exposing unnecessary sensitive information.

## 33. State and Ownership Rules

Evidence ownership shall transfer to the Evidence Engine after successful creation.

Before creation, input data remains owned by the caller.

After creation:

- the Evidence Engine owns the validated Evidence representation;
- caller-owned mutable structures shall no longer affect Evidence;
- internal storage shall remain private;
- retrieved Evidence shall remain immutable.

The Evidence Engine shall defensively copy supported mutable input structures during creation.

No external caller shall receive a mutable reference to internal Evidence state.

Ownership shall not depend on object identity, memory location or garbage-collection behavior.

## 41. DESIGN HARDENING v1.0 — FROZEN DECISIONS

This section records the decisions made during final design hardening and makes them implementation constraints for MOD-006 v1.0.

### 41.1 Identity
`evidence_id` is SHA-256 over the exact canonical identity byte sequence. Identity-bearing fields are exactly timestamp, source, type, value, symbol, and timeframe. Metadata is excluded unless a future specification explicitly promotes a field.

### 41.2 Canonical Representation
Canonical representation is versioned as `ORION-EVIDENCE-1`.

The exact canonical representation shall begin with the ASCII prefix:

`ORION-EVIDENCE-1|`

The trailing `|` is part of the canonical representation and is included in the SHA-256 input.

The six identity-bearing fields shall follow the prefix immediately and shall use the exact field framing and ordering defined in Section 7.

Finite floating-point values shall use IEEE-754 binary64 semantics and the exact Python `float.hex()` representation defined in Section 24.

Mapping keys shall be sorted by their UTF-8 encoded key bytes and shall themselves be encoded using the canonical string representation `S:<byte-length>:<UTF-8 bytes>` defined in Section 24.

Golden canonical byte sequences and SHA-256 outputs shall be tested as contract tests.

Changing the canonical representation is a breaking identity change and requires a new specification/version decision.

### 41.3 Optional Market Context
Absent `symbol` and `timeframe` are represented explicitly as null. They are not inferred, aliased, or case-normalized.

### 41.4 Query Ranges
Timestamp ranges use `[start, end)`: start inclusive, end exclusive. `start >= end` is invalid.

### 41.5 Retrieval
`get(evidence_id)` returns the immutable Evidence object when present and `None` when absent. A strict presence-required operation may raise `EvidenceNotFound`.

### 41.6 String Normalization
For source, type, symbol, and timeframe: input must be a string; leading/trailing whitespace is removed; empty results are rejected; internal content and case are preserved.

### 41.7 EventBus Contract
The EventBus receives the immutable Evidence object after successful storage. EventBus transport does not participate in identity generation, validation, or duplicate detection.

Sequence:
`validate → normalize → canonicalize → identity → duplicate check → store → publish`

### 41.8 Publication Failure
If publication fails after storage, stored Evidence remains valid and retrievable; the failure is observable; no replacement or second identity is created; retry/recovery belongs to higher-level orchestration.

### 41.9 Error Contract
Typed exceptions shall correspond to the semantic error categories in Section 21. Error messages shall identify the violated rule without exposing unnecessary payload contents.

### 41.10 Test Contract
Tests shall verify the design contract rather than invent it. At minimum: canonical serialization golden cases, SHA-256 golden identities, timezone normalization, bool/int/float distinction, nested determinism, metadata exclusion, string normalization, `[start, end)` boundaries, deterministic ordering, duplicate rejection, deep immutability, store-first/publish-second behavior, publication-failure retention, and the full regression suite.

### 41.11 Approval Gate
After this hardening is accepted, the document may transition from `DESIGN — DRAFT FOR REVIEW` to `DESIGN — APPROVED FOR IMPLEMENTATION`. No production implementation shall begin before that approval gate is explicitly passed.
